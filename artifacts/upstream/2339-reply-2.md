@overcookedlobster Your `gbmprobe` result reproduces something I had measured independently, with
a much clumsier harness, and I want to confirm it before disagreeing with the conclusion you draw
from it.

**Confirmed: Waydroid's bundled Mesa `libgbm` cannot allocate any YUV format.** Same set, same
outcome, on entirely different hardware (Broadwell-Y / HD 5300, HP Envy x2, Fedora 44,
Waydroid 1.6.3, LineageOS 20 / SDK 33, UVC webcam rather than v4l2loopback). Your probe is the
cleaner demonstration — calling the stable gbm ABI with gralloc out of the path is exactly the
right way to establish it, and it settles the question much more directly than reading
allocation logs does.

**But the R8 fallback buffer is not the reason the camera fails, and it does not have to be
grayscale.** I have a working camera on that fallback path. Live preview, correct colour,
`screencap` of a real scene rather than a black frame, `Failed to map the buffer` and
`format coversion failed` both at zero occurrences.

## The actual defect is an ordering bug in the import, not the R8 allocation

`gbm_mesa_bo_import()` means to pass the buffer's byte size as a width:

```c
if (wr->get_gbm_format(s_format) == 0) {
        s_width = bo->meta.total_size;   /* still 0 at this point */
        s_height = 1;
        s_format = DRM_FORMAT_R8;
}
```

`meta.total_size` is zero there. minigbm's `drv_bo_import()` calls the backend's `bo_import`
hook **before** it accumulates the per-plane sizes:

```c
bo = drv_bo_new(drv, ...);                  /* calloc -> total_size = 0 */
ret = drv->backend->bo_import(bo, data);    /* gbm_mesa_bo_import runs HERE */
...
for (plane = 0; plane < bo->meta.num_planes; plane++) {
        seek_end = lseek(data->fds[plane], 0, SEEK_END);
        ...
        bo->meta.total_size += bo->meta.sizes[plane];   /* only now */
}
```

Verified against `drv.c` and `gbm_mesa_driver/gbm_mesa_internals.cpp` at `a9367e8`, the commit
the shipped `libgbm_mesa_wrapper.so` fingerprints to.

So the wrapper asks for a **0 × 1** image. That is rejected, `gbm_bo_import` returns NULL,
`gbm_bo_map` is called on a NULL bo and returns NULL, and the HAL receives the all-zero plane
layout everyone in this thread is looking at:

```
formatConvert: unsupported flexible yuv layout y 0x0 cb 0x0 cr 0x0 y_str 0 c_str 0 c_step 0
```

Measured in the camera provider, with the width visible:

```
TRACE import in : fd=14 0x1 fmt=0x20203852 stride=1280 mod=0x0
                     ^^^ width=0, height=1
```

The fix sizes the buffer from the dmabuf itself and reshapes it into a 2D texture — using
`lseek(SEEK_END)`, which is the mechanism minigbm already trusts for this, twenty lines below
the hook:

```c
if (drm_format == DRM_FORMAT_R8 && height == 1) {
        off_t size = lseek(buf_fd, 0, SEEK_END);
        if (size > 0) {
                lseek(buf_fd, 0, SEEK_SET);
                height = DIV_ROUND_UP((uint32_t)size, GBM_MESA_1D_WIDTH);
                width  = GBM_MESA_1D_WIDTH;      /* 4096 */
                stride = GBM_MESA_1D_WIDTH;
        }
}
```

Full write-up and patch: **android_external_minigbm#3**. It builds with the NDK against minigbm
`a9367e8` — no AOSP tree — and ships as one `.so` per ABI through the vendor overlay.

## Where that leaves `minigbm_intel`

If the import is the whole defect, then the transplant you did — and the SurfaceFlinger
`Unable to generate SkSurface` abort it ran into, and the newer-Mesa pairing it needs — is work
the bug does not actually require. That would be worth knowing before anyone else follows that
path, which is the main reason I am writing.

**What I cannot claim from my own machine:** my verification client is Open Camera, and yours is
CameraX / Aperture. I have not established which path Open Camera's preview takes through the
buffer, so I cannot tell you from here that a CameraX `ImageAnalysis` stream is equally happy
with an R8-backed flexible-YUV buffer. Your grayscale/stride objection is the right question to
ask of it; I just have a working preview that says the answer is not automatically "no". If you
apply the patch from #3 to your tree, that test would settle it on the hardware and with the app
that actually motivated the concern — and it would settle it better than anything I can run.

A second, smaller thing you could settle in the same pass: the patch also clamps the map
rectangle, and I have never been able to confirm that half is needed. Dropping just the clamp
block from the map op, with the import fix in place, would tell us whether the diff that belongs
upstream is smaller than what #3 currently proposes.

## Two separate sharp edges, so nobody conflates them with the above

**`format coversion failed!` has more than one cause.** Besides the zero layout, the external
camera HAL's conversion path fails outright on modes above 1280×720: it selects the largest
advertised mode, starts 1920×1080@30 MJPG, and then fails in conversion with the same message —
LED on, preview black. Removing every `Limit` above 720p from
`vendor/etc/external_camera_config.xml` is what makes a preview appear on a 1080p-capable
webcam. If you are chasing this message, check which of the two you have before assuming it is
the gralloc bug. I intend to file that separately.

**`ANDROID_LENS_FACING` is hardcoded to `EXTERNAL`**, which @overcookedlobster also notes. Apps
that enumerate looking for a rear camera find none; Google Lens dereferences the result without a
null check and dies during enumeration, before ever issuing a `CONNECT`. On a device whose only
camera is a webcam, `BACK` and `FRONT` are both lies and `EXTERNAL` satisfies nothing, so this
wants to be a property rather than a compile-time constant. Also filing separately.
