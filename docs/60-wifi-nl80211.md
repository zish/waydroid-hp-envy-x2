# 60 — Wi-Fi via nl80211: the null that made four other fixes pointless

*2026-10-01. Closes the nl80211 items left open at the end of
[docs/59](59-wifi-stage5-polish.md), and the data race docs/59 recorded as a design question
rather than a patch. **All verified on bigtab01 against `iw` as ground truth.** The headline is
not any of the four measurements: it is that `getDeviceWiphyCapabilities` returned null, and that
one null makes Android's throughput predictor return 0 before it looks at the PHY, the channel
width or the spatial streams — so the obvious plan of "report the negotiated PHY" would have
shipped a value nothing read.*

## One-paragraph summary

[docs/59](59-wifi-stage5-polish.md) left four items whose answer was "a few hundred lines of
nl80211": the negotiated PHY reported as UNKNOWN, the RX bitrate reported as the TX one, packet
counters reading zero, and an RSSI with NetworkManager's poll lag under it. All four are now read
from the radio by a new [wifi/Nl80211.cpp](../wifi/Nl80211.cpp) that speaks raw netlink and **adds
no runtime dependency** — the binary still needs exactly the six shared libraries 1.0.1 needed.
Three of the four landed. The fourth did not, and the reason is worth more than the fix would have
been: **Android never calls `getPacketCounters` on this host at all.** Separately, and this is the
part that changes how the rest should be read, `ThroughputPredictor.predictThroughput`'s *first*
act is to return 0 if the wiphy capabilities are null — which they were, from a one-line stub that
had sat unnoticed through five stages because returning null is legal and logs nothing. Answering
it is what lets any of the other work reach the framework, and it is also what turned `Max
Supported Tx/Rx Link speed` from `-1` into real numbers.

## The null, and why nobody found it for five stages

[Wificond.cpp](../wifi/Wificond.cpp)'s handler was three lines and a comment that was true:

```c
/*
 * Null is a legal answer -- WifiNative checks for it -- and it is the
 * honest one until there is a real radio description to hand up.
 */
GDEBUG("getDeviceWiphyCapabilities(%s) -> null", name.c_str());
writeNullParcelable(&writer);
```

`WifiNative` does check for null, so this never threw, never logged a warning, and never appeared
in any of the five stages' test output. What it costs is one branch deep inside the framework,
disassembled out of this image's own `service-wifi.jar`:

```
com.android.server.wifi.ThroughputPredictor.predictThroughput:
  |000e: if-nez v1, 0016                 <- v1 = DeviceWiphyCapabilities
  |0010: const-string v0, "Null device capabilities passed to throughput predictor"
  |0012: invoke-static {v6, v0}, Landroid/util/Log;.e
  |0015: return v5                       <- v5 = 0
```

The predictor returns **0** before reading its other nine arguments. So the plan this session
started with — report the negotiated PHY, which is what `getConnectionCapabilities.technology`
asks for — would have put a correct value into a field the predictor never reaches. The two
changes are one change, and the order in which they were discovered was luck: the parameter list
of `predictThroughput` was being read to find out *how* `technology` is consumed.

It was logged exactly once on this host, at a timestamp that makes the before/after free:

```
10-01 11:40:41.318  299  452 E WifiThroughputPredictor: Null device capabilities
                                                        passed to throughput predictor
```

11:40:41 is the last run of the 1.0.1 binary. It has not recurred since the new one started.

### The parcel layout is not the shape the other parcelable in this daemon uses

`DeviceWiphyCapabilities` is a **hand-written framework `Parcelable`, not a stable-AIDL one**, so
its `createFromParcel` reads fields straight off the parcel with **no leading size word** — where
`ConnectionCapabilities` in [Supplicant.cpp](../wifi/Supplicant.cpp) has one. Getting that
distinction wrong is precisely the Stage 4 failure that killed `system_server` on every
association, so the layout was disassembled rather than inferred:

```
DeviceWiphyCapabilities.writeToParcel:
    writeBoolean m80211nSupported
    writeBoolean m80211acSupported
    writeBoolean m80211axSupported
    writeBoolean m80211beSupported
    writeBoolean mChannelWidth160MhzSupported
    writeBoolean mChannelWidth80p80MhzSupported
    writeBoolean mChannelWidth320MhzSupported
    writeInt     mMaxNumberTxSpatialStreams
    writeInt     mMaxNumberRxSpatialStreams

DeviceWiphyCapabilities$1.createFromParcel:
    7 x readBoolean, then 2 x readInt      <- no size word
```

Two traps in that order. The **320 MHz flag is written seventh**, after 80+80 — not in the
alphabetical order the class declares its fields in, which is the order `dexdump` prints them and
therefore the order anyone reading the field list would assume. And **tx streams come before rx**.
`Parcel.writeBoolean` is `writeInt(b ? 1 : 0)`, so the wire form is the non-null marker followed
by nine int32s.

The framework reads these back through two methods that walk *down* from the best standard until
one is supported, so a radio that under-reports its capabilities gets its PHY silently clamped:

```
isWifiStandardSupported: 1 -> always true   4 -> 11n    5 -> 11ac   6 -> 11ax   8 -> 11be
predictThroughput tries: 8, then 6, then 5, then 4, then falls back to 1 (LEGACY)
```

## The negotiated PHY

`technology` wants the PHY **this station settled on with this AP**, and NM structurally does not
have it. Its only candidate is `AccessPoint.MaxBitrate`, which is the AP's *advertised* capability
— measured on bigtab01, APs advertise 1170 Mb/s on a 20 MHz 2.4 GHz channel, which is not
optimistic but physically impossible, so the number cannot be inverted into a PHY. Nor would the
AP's capability answer the question: the technology is the **minimum** of the two ends, and this
machine's card is a 2x2 HT/VHT Broadwell-era part that negotiates VHT against an HE AP.

nl80211 carries it as the **choice of MCS attribute** inside `NL80211_STA_INFO_TX_BITRATE`:
`RATE_INFO_MCS` means HT, `VHT_MCS` means VHT, `HE_MCS` means HE, `EHT_MCS` means EHT, and a rate
with none of them is a legacy 802.11a/b/g rate. That is the negotiated PHY by construction rather
than by inference — it is what the driver is actually clocking frames at.

The enum was disassembled rather than assumed, because `ConnectionCapabilities.technology` is typed
as a bare `int` in the AIDL:

```
SupplicantStaIfaceHalAidlImpl.getWifiStandard(t):
    1 -> 1 (LEGACY)   2 -> 4 (11N)   3 -> 5 (11AC)   4 -> 6 (11AX)   5 -> 8 (11BE)   else 0
```

So the wire value is `WifiTechnology`, and the five values it accepts are exactly the five `Phy`
can be. Anything unrecognised maps to 0, which still matters: UNKNOWN makes the predictor fall
back to a floor, where a *wrong* standard makes it predict confidently and wrongly.

**The two directions can disagree and the link is the better of them.** On this machine the TX
direction ran HT while the AP had dropped RX to a legacy CCK rate; that is an HT link.
`Phy` is ordered so this is a `std::max`.

## Why raw netlink and not libnl

| | libnl | raw `AF_NETLINK` |
|---|---|---|
| on this dev box | **absent** — no `libnl-genl-3.0` in pkg-config, no `libnl-3.so` | `<linux/nl80211.h>` present, it is kernel uAPI |
| new runtime deps | 2 | **0** |
| new `.so` for `--deps` to copy off the host | 2 | 0 |
| new pkg-config names in the `--rpm` arm | 2 | 0 |
| new RPM `Requires` | 2 | 0 |
| code it saves | ~350 lines of TLV walking with no interesting cases | — |

The ABI argument that justifies vendoring libgbinder headers **does not transfer**, and that is the
load-bearing half of the reasoning. libgbinder's layout can change between releases, so the build
pins it to the host's exact version and copies the host's own `.so`. The netlink **wire format is a
kernel ABI**: attributes are append-only and the kernel never renumbers one. Compiling against this
box's fc42 headers and running against the host's fc44 kernel is safe by the kernel's own
compatibility rule, and the worst case is not knowing about an attribute added after our header was
written. `EHT_MCS` is already in it, so even 802.11be is covered.

Confirmed on the built binary — the same six as 1.0.1, and no seventh:

```
libgbinder.so.1  libglibutil.so.1  libgio-2.0.so.0
libgobject-2.0.so.0  libglib-2.0.so.0  libc.so.6
```

### `GET_WIPHY` has to be a split dump, and that is not an optimisation

A non-dump `GET_WIPHY` asks the kernel to describe the whole radio into one 4 KiB skb —
`nl80211_get_wiphy` allocates exactly `nlmsg_new(4096)` — and a two-band card with a full channel
list does not fit, so the call fails with `-ENOBUFS` rather than returning a short answer. The
split dump is what `iw` itself uses: the kernel spreads the attributes across several `NEW_WIPHY`
messages. Splitting means an attribute can appear in more than one message, so everything the band
parser computes is accumulated — OR for the capability flags, max for the stream counts — which
happens to be the correct semantics for the question anyway, since "this radio can do VHT" is true
if any band can.

## Measured, against `iw` as ground truth

The parser was validated standalone before any of it was wired into the daemon, which is the
check worth having: a disagreement here would otherwise have surfaced three layers up as an
Android-side oddity.

```
                 parser                      iw
signal           -63 dBm (avg -62)           -63 dBm (avg -62)
tx               39000 kbps HT nss 2         39.0 MBit/s MCS 10      (MCS 10 -> 2 streams)
rx               72200 kbps HT nss 1         72.2 MBit/s MCS 7       (MCS 7  -> 1 stream)
tx packets       10235                       10238                   (sampled moments apart)
tx failed        39                          39
tx retries       2495                        2495
rx packets       44977                       44977
connected        8271 s                      8271 s

wiphy            ht=1 vht=1 he=0 eht=0       HT MCS 0-15, VHT 2 streams,
                 160=0 80+80=0 320=0         "neither 160 nor 80+80", no HE
                 2x2 streams
```

HT has no `NSS` attribute — the stream count is encoded in the MCS index itself (0-7 is one stream,
8-15 two), which is why that one value is derived and every other PHY's is read.

### End to end, in Android's own words

| | 1.0.1 | 1.1.0 |
|---|---|---|
| `Wi-Fi standard` | `0` (UNKNOWN) | **`4`** (11N) |
| `Link speed` / `Tx` / `Rx` | `130` / `130` / `130` Mbps | **`144` / `144` / `1`** — independent |
| `Max Supported Tx Link speed` | `-1` Mbps | **`144`** Mbps |
| `Max Supported Rx Link speed` | `-1` Mbps | **`72`** Mbps |
| score history `txLinkSpeed,rxLinkSpeed` | `130, 130` | **`144,24` `52,48` `57,65`** — moving apart |
| `Null device capabilities` in logcat | fires | absent |
| RSSI vs the radio | NM's, measured 3 dB low | **agrees 4 of 4 samples** |

The RSSI test is the one worth spelling out, because "both are negative numbers near each other" is
exactly the standard that let a 10 dB error survive five stages. Five consecutive samples, with
NM's quality put through 1.0.1's own exact inverse for comparison:

```
iw=-62dBm  nm_quality=57->-65dBm  android=-63dBm
iw=-61dBm  nm_quality=59->-64dBm  android=-61dBm
iw=-62dBm  nm_quality=58->-65dBm  android=-62dBm
iw=-61dBm  nm_quality=60->-64dBm  android=-61dBm
iw=-62dBm  nm_quality=62->-62dBm  android=-62dBm
```

Android tracks the radio and not NM — exactly, in four of five, and the fifth is 1 dB. NM is
consistently 3 dB low, which is [docs/59](59-wifi-stage5-polish.md)'s "NM's `Strength` for the
connected AP lags" finding quantified: it is not noise, it is a bias, and it was sitting inside the
±3 dB tolerance the old test allowed.

## What did not close, and one thing that cannot close here

**`getPacketCounters` is never called on this host.** The handler now returns
`NL80211_STA_INFO_TX_PACKETS` and `TX_FAILED` instead of a hardcoded `{0, 0}`, and that is correct
and cost nothing — but Android only asks around a **link probe**, and `SendMgmtFrame` has **never
been called in this daemon's entire journal**. So the fix is latent rather than live. It is kept
because the alternative is a handler that lies if the framework ever does ask, and the call is now
logged unconditionally so that "never called" is visible instead of indistinguishable from
"returns zero".

**The `tx_good`/`tx_retry`/`tx_bad`/`rx_pps` columns in `dumpsys wifi` cannot be fixed at this
seam at all.** They come from `IWifiStaIface.getLinkLayerStats`, which is the **vendor HAL** —
something this daemon does not serve and which was never in scope. docs/59 listed the zero counters
as one open item; it is really two, and only the wificond half was ever reachable from here.

**`txTput` and `rxTput` are still a constant.** They read `12` and `30` across every score-history
row regardless of RSSI or link speed, where docs/59 recorded a flat `10`/`10`. The predictor's hard
early-return is definitely gone — the log line proves that — but a value that does not move with
conditions is not a prediction, and `12000`/`30000` Kbps is also what `NetworkCapabilities` reported
as its link bandwidths *before* any of this work. **So the honest claim is narrow: the predictor is
no longer short-circuiting, and whether it is now computing is not established.** The most likely
reason it still would not be is the missing link-layer stats above. Not chased further.

## The deploy trap: `build.sh --install` no longer reaches the running daemon

Worth its own section because it cost a wrong conclusion mid-session and will cost the next person
the same one.

`wifi/build.sh --install` writes `/usr/local/bin/waydroid-wifid`, which is correct for an
`rpm-ostree` host — `/usr/local` is a symlink to the writable `/var/usrlocal`. But since the
packages landed ([docs/59](59-wifi-stage5-polish.md), "16 packages"), the **active unit is the
packaged one**:

```
FragmentPath=/usr/lib/systemd/system/waydroid-wifid.service
ExecStart=/usr/bin/waydroid-wifid
/usr/bin/waydroid-wifid  ->  owned by waydroid-ext-wifid-1.0.1-1
```

So `--install` followed by `systemctl restart` installs a new binary, restarts the service, reports
success, and **runs the old code** — and `/usr/bin` is on the read-only ostree `/usr`, so it cannot
simply be overwritten either. The symptom was a journal still printing `technology UNKNOWN` from a
daemon that had just been "installed"; what gave it away was the *log string*, not any version
number.

docs/59 documented the shadowing in the other direction — hand-placed `/etc` units shadowing
packaged ones for `media`, `cage` and three others — and recorded that the Wi-Fi three had migrated
to packages. **Nobody wrote down that migrating them made the by-hand install path inert.**

For a test before packaging, a drop-in is the reversible way through:

```ini
# /etc/systemd/system/waydroid-wifid.service.d/99-local-binary.conf
[Service]
ExecStart=
ExecStart=/usr/local/bin/waydroid-wifid $WAYDROID_WIFID_ARGS /dev/binderfs/binder
```

and then remove the directory once the RPM carrying the same binary is installed. **That drop-in is
on bigtab01 right now**, running a binary byte-identical to the one in
`waydroid-ext-wifid-1.1.0`; the package is built but deliberately not deployed, because
`rpm-ostree install` wants a reboot and this is a kiosk host.

## Closing docs/59's data race, and why a mutex rather than a handoff

[docs/59](59-wifi-stage5-polish.md) left this open "because fixing it properly means deciding
whether the backend gets a lock or whether handlers post work to the main loop and wait — a design
question, not a patch." The nl80211 work forces the decision, because it adds a third caller on a
binder thread. The decision, and the argument that settles it:

**Post-and-wait can deadlock here.** The main loop itself calls into Android — it sends `COMPLETED`
to the supplicant callback from `onHostLinkEvent`. A binder thread blocking on the main loop while
the main loop blocks on a binder transaction is a cycle with no timeout on it. A mutex has no such
cycle: nothing held under it ever waits on another thread of ours, only on D-Bus and on netlink,
which are timeout-bounded calls to another process.

So `mIfname`, `mDevPath` and `mSelectorMac` are guarded by a `std::recursive_mutex` — recursive
because `selectDevice()` holds it across `wifiDevicePath()`. The three call sites docs/59 named
(`getMacAddress`, `connect`, `disconnect`) all reach the shared state only through
`wifiDevicePath()`, so locking there covers them.

**The nl80211 path shares no mutable state at all**, which is better than being locked. Every call
into [Nl80211.h](../wifi/Nl80211.h) is keyed by an interface **index** held in a
`std::atomic<int>`, not by a name. That is a design choice rather than an interface convenience: an
`int` is something a binder thread can be handed without reading a `std::string` the main loop can
rewrite. The class serialises its own socket with its own mutex, so several binder threads may call
it at once.

Two smaller guards came out of the same reasoning. The netlink socket carries a
**2-second `SO_RCVTIMEO`**, because a handler that blocks forever does not lose one value — it
holds a thread from `system_server`'s binder pool until Android's own transaction timeout fires.
And `refreshIfindex()` **clears** the index when a name stops resolving rather than leaving the
previous radio's behind, because querying nl80211 with a stale index is how a daemon reports
another interface's signal as this one's.

## The test that would have started crying wolf

[bin/wifi-test.sh](../bin/wifi-test.sh)'s RSSI check compared Android's value against NM's
`Strength` put through `-100 + 3*quality/5`, passing within ±3 dB. **That check was correct for
1.0.1 and is wrong for 1.1.0**: the reference moved to the driver's dBm, and NM was just measured
3 dB low — sitting exactly on the tolerance boundary. Left alone it would have begun failing
intermittently on a working daemon, which is the failure docs/59 had to fix in three other scripts.

It now compares against `iw` as primary with a ±2 dB tolerance, keeps NM's formula as the
fallback-path reference, and gains a second regression signature: matching NM's formula *exactly*
and repeatedly while the radio reads something else means the nl80211 overlay is not running. Two
new checks came with it — the PHY not being UNKNOWN, and `Max Supported Tx` being positive, which
is the cheapest possible probe for "did `getDeviceWiphyCapabilities` answer".

Full run on bigtab01: **PASS**, including `Android -60 dBm, radio -60 dBm (4 of 4 samples agreed)`.

## The T3U is not a configuration this project supports

Recorded here because three earlier documents can be read as implying otherwise. The TP-Link Archer
T3U that [docs/34](34-wifi-second-radio.md) added was **a back-door management link to bigtab01,
used so that Wi-Fi connectivity testing could not strand the machine** — not a second radio this
project intends to drive. It is not plugged into the host any more.

So **the rtw88 wedge is closed as out of scope**, not left open-and-unobserved: it is a fault in a
driver for an adapter this project does not target. [bin/wifi-radio-reset.sh](../bin/wifi-radio-reset.sh)
stays, scoped to that adapter, and the `nmcli connection up` discriminator stays mandatory before
running it — both for anyone who does use a second radio.

What does **not** change is the multi-radio machinery itself. `--device`, the factory-MAC pinning
and `carriesHostDefaultRoute()` are what keep Android off the host's own link (trap 5 of
[docs/33](33-wifi-stage4.md)), and that guard matters more on a single-radio host, not less.

## Still open

- **The host's two ~10-minute link drops of 2026-09-18 are still uninvestigated.**
- **Scan staleness after repeated daemon restarts** — docs/35's false trail, still not diagnosed.
- **The wrong-password path is still unproven.** NM reports `AuthFailed` through
  `Device.StateChanged`'s reason and the shim maps it, but nobody has typed a wrong password and
  watched Android render it. nl80211's `CMD_CONNECT` status codes would be a second, better source
  and are not wired up.
- **Link-layer stats need a vendor HAL**, so `tx_good`, `tx_retry`, `tx_bad` and `rx_pps` stay zero
  and the framework's throughput prediction stays un-refined. See above.
- **`getPacketCounters` is latent**, because nothing calls it here.
- **Scan-result RSSI still comes from NM**, not from nl80211. `GET_SCAN` was deliberately left
  alone: NM's AP objects carry the `known` flag and the `tsf` logic that
  [docs/35](35-wifi-stage5.md) had to get right, and a second scan cache would diverge from them.
- **Channel lists still come from NM**, not from `GET_WIPHY`'s frequency attributes. Working, so
  not touched — but the parser that would answer it is now in the tree.
- **`waydroid-ext-wifid-1.1.0` is built and not deployed**, and a drop-in is standing in for it.
  See the deploy-trap section.

